# Bone Dry — "Across Aqua": prove the schema is standardized (for Antigravity)

The oracle-deviation pass (Chainlink feeds, per-slice deviation, badges,
standalone `Beacon.sol`) is done, verified, and merged. This plan is smaller
and different in kind: not a new feature, a **proof of a claim already made**.

## The claim, and why it needs proving rather than just stating

`subgraph/schema.graphql` has this line, written before this plan existed:

> "this is that index, and the shape below is proposed as a reusable schema
> any Aqua app can adopt rather than something specific to Bone Dry"

That claim is true **right now**, independent of anything in this plan — it
was checked directly against the live subgraph before this plan was written:

```
{ strategies(first: 1000) { app } }
```
returns strategies under **two distinct `app` addresses** on Base mainnet —
`0x111111...ac0de` (1inch's own router, 440 strategies) and a second,
unrelated address (`0x1111113db0e0ef9d0e3a50d5f094a3a57a26c0de`, 1 strategy)
that is neither Bone Dry's router nor 1inch's main one. Our subgraph
listens to Aqua's own contract events, not events scoped to our router — so
it was *already* indexing a second, real, independent Aqua consumer,
without anyone building for that on purpose.

This plan makes that fact visible instead of leaving it sitting undiscovered
in a GraphQL response. It targets The Graph's own stated judging language
directly: *"one query pattern spanning many protocols."*

## Task 1 — A query that groups by app instead of assuming one

**Goal:** a function that answers "how many live strategies exist, broken
down by which app shipped them" — using the data already indexed, no schema
change.

### What to add

In `web/lib/graph.ts`, add:

```ts
const APPS_QUERY = `
  query Apps($first: Int!) {
    strategies(where: { active: true }, first: $first) {
      app
      maker { id }
    }
  }
`;

export type AppBreakdown = {
  app: Address;
  /** Whether this is the app Bone Dry's own router points at -- the rest
   *  are other Aqua consumers this subgraph happens to also index, since it
   *  listens to Aqua's own events rather than filtering to one app. */
  isOurs: boolean;
  activeStrategies: number;
  distinctMakers: number;
};

/**
 * Every app currently shipping live strategies on Aqua, per the same index
 * that already answers Bone Dry's own coverage questions. This is not a
 * new capability -- it is the existing schema, queried without the `app`
 * filter every other query in this file applies. Proof that the schema
 * generalizes, not a new feature.
 */
export async function appBreakdown(n: Network, ourApp: Address, first = 1000): Promise<AppBreakdown[] | null> {
  if (!(await indexFresh(n))) return null;
  const data = await gql<{ strategies: { app: Address; maker: { id: Address } }[] }>(
    n, APPS_QUERY, { first }
  );
  if (!data) return null;

  const byApp = new Map<string, { makers: Set<string>; count: number }>();
  for (const s of data.strategies) {
    const key = s.app.toLowerCase();
    const entry = byApp.get(key) ?? { makers: new Set<string>(), count: 0 };
    entry.count += 1;
    entry.makers.add(s.maker.id.toLowerCase());
    byApp.set(key, entry);
  }

  return [...byApp.entries()]
    .map(([app, v]) => ({
      app: app as Address,
      isOurs: app === ourApp.toLowerCase(),
      activeStrategies: v.count,
      distinctMakers: v.makers.size,
    }))
    .sort((a, b) => b.activeStrategies - a.activeStrategies);
}
```

Match this file's existing conventions exactly (it already has `indexFresh`,
`gql`, and this general shape used four other times in the same file — read
`positionsForMaker` right above where you add this, and mirror its error
handling, not a new pattern).

### Verification

1. `npx tsc --noEmit` clean.
2. Run a standalone check (same pattern as the oracle plan's Task 1 smoke
   test) against Base mainnet and paste the actual result. It should show
   at least two distinct `app` entries — if it shows only one, something

## Task 2 — `/api/apps`

**Goal:** a route exposing Task 1's function, following the exact
available/reason pattern `/api/coverage` already uses.

### What to add

New file `web/app/api/apps/route.ts`:
```ts
import { networkFrom } from "@/lib/networks";
import { appBreakdown } from "@/lib/graph";
import { j, fail, chainFailure } from "@/lib/json";

export const dynamic = "force-dynamic";

/**
 * GET /api/apps?chain=
 *
 * Every app currently shipping live Aqua strategies, per the same subgraph
 * that answers Bone Dry's own coverage view -- proof the schema this
 * project proposed as a reusable Aqua standard actually generalizes, not
 * an assertion about it.
 */
export async function GET(req: Request) {
  try {
    const url = new URL(req.url);
    const n = networkFrom(url.searchParams.get("chain"));
    const apps = await appBreakdown(n, n.router);

    if (apps === null) {
      return j({
        available: false,
        reason: !n.graphUrl
          ? `no subgraph is indexing ${n.label} yet`
          : `the ${n.label} index is unavailable or still catching up`,
        apps: [],
      });
    }

    return j({ available: true, apps });
  } catch (e) {
    const unreachable = chainFailure(e);
    if (unreachable) return unreachable;
    return fail((e as Error).message, 500);
  }
}
```

Check `web/lib/json.ts` and an existing route (`coverage/route.ts`) for the
exact error-handling shape before assuming the above is complete — this
plan's draft may be missing an import or a case an existing route already
handles; match it, don't diverge.

  against a state where the second app has since disappeared): render it
  plainly, do not hide the section or claim more apps than exist. The
  honest number is the whole point of this feature.
